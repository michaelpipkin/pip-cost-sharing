Test Suite Overhaul — Design

pip-cost-sharing · 2026-10-19 · Status: draft for approval

Tags: [my call] marks decisions Claude made that the owner has not explicitly confirmed. Everything else was decided in conversation with the owner.

1. Intent

The owner makes small, targeted changes to the app and wants to run the unit and e2e tests for the area they touched and trust the result: a pass means that area still works, a failure means the change broke something — not that a test went stale.

Today that trust doesn't exist for e2e. The unit suite is healthy (1,471 tests / 113 files, all passing, ~14 s), but the e2e suite (~79 Playwright tests, 10 spec files) was written in Feb 2026 and ~790 commits have landed since. 15 of the 124 data-testids the e2e code references no longer exist in the app. Several features have never had e2e coverage.

The owner's stated failure mode for the future: the suite goes stale again if a major update is done without updating the tests. The process changes in §7 exist to prevent that.

2. Goals, non-goals, anti-goals

Goals

  1. Repair the existing e2e suite so it passes against the current app.
  2. Add e2e coverage for features that never had any: rental expenses, memorized expenses, the split page, account settings, group invites, receipt scanning, guided tours, admin pages (and categories/members if not adequately covered by the existing groups spec).
  3. Fill unit-test gaps, prioritising substantive untested code (list in §6).
  4. Per-area test runs: one command, owner names the area, runs that area's unit and e2e tests.
  5. A shared, deterministic e2e data set built once at suite start, designed so no test's writes can break another test.
  6. Keep it from drifting: a CLAUDE.md rule and an e2e section in the pip-angular-testing skill.

Non-goals

  • No CI integration. Tests are run locally only; the deploy workflow is not changed.
  • No automatic "which files changed in git" area detection. The owner names the area explicitly (so it works as a sanity check with a clean tree).
  • No mobile-viewport or non-Chromium projects (they stay commented out in playwright.config.ts).
  • No numeric coverage threshold is enforced. [my call]

Anti-goals (would make this a failure even if every test is green)

  • Tests bent to match bugs. If a failure looks like a real app bug, the builder stops and reports it to the owner; it is never "fixed" by changing the assertion to match broken behaviour.
  • Flaky tests. A test that sometimes fails destroys the trust this work is buying.
  • Order-dependent tests. Any test must pass whether its area is run alone, with the full suite, or with 4 parallel workers.
  • Reintroducing per-test emulator wipes (the original parallel-worker problem; see §4).

3. Constraints

  • Package installs and network downloads are done by the owner, never by Claude (TLS interception breaks them in this environment). Known pending: pnpm exec playwright install chromium (Playwright 1.64.1 needs Chromium build 1248; only 1243 is installed — this alone made every e2e test fail in 2 ms) and pnpm add -D @vitest/coverage-v8 (for coverage reports). If the design needs a new dependency (e.g. firebase-admin at the repo root), list it and hand off.
  • E2E runs on its own, isolated emulators (owner decision). The owner runs several projects' emulators on the default ports and uses pnpm emu:data for manual development. E2E must never touch those. Playwright starts a dedicated emulator suite on non-default ports under a demo-* project ID (so nothing can ever reach a real project), plus a dev server built with an Angular configuration that points at those ports, and shuts them down afterwards. Consequences:
    • The dev emulators can stay running during e2e; e2e never wipes the owner's dev data.
    • No owner confirmation is needed before e2e runs, which is what makes the CLAUDE.md "run the area's tests before done" rule workable.
    • The functions emulator must load this project's functions under the demo project ID; the functions build must be current before a run (the e2e start-up should build or verify it).
    • The dev server for e2e uses its own port too, so it doesn't collide with a manually running pnpm start on 4200.
    • Ad-hoc probes of the default ports (dev emulators) still require the owner's go-ahead.
  • Any Admin SDK code must set FIRESTORE_EMULATOR_HOST, FIREBASE_AUTH_EMULATOR_HOST and FIREBASE_STORAGE_EMULATOR_HOST before initializeApp — a missed one once hit production Auth. scripts/db/emulator-lib.ts currently sets only the Firestore one.
  • Unit tests follow the existing pip-angular-testing skill (no vi.mock, path-aliased Firebase mocks, never vi.resetAllMocks, etc.).
  • Project conventions from CLAUDE.md apply to any app code touched (signals, protected readonly inject, no rxjs, @if/@for, pnpm).
  • E2E tests must never send real email or depend on external downloads. Today, under the functions emulator, getSmtpPassword() (functions/src/common.ts) returns the real SMTP_PASSWORD from functions/.env, so the mail-queue sender delivers real email via Office 365 as admin@pipsplit.com — any e2e run that triggers invites, payment notifications or the mail queue sends real messages (to fake addresses, which bounce). This must be neutralised for e2e before any e2e run that exercises those flows; the builder picks a mechanism that affects e2e only (e.g. an env flag the emulator honours to log instead of send). Receipt scanning runs tesseract.js inside scanReceipt (functions/src/receipt-ocr.ts); its language-data download is the external dependency to stub or cache.

4. E2E test data: the shared data set (owner decision)

History. Running with multiple workers, tests that cleared emulator data before/after themselves wiped data out from under tests running in other workers. The fix was: clear the emulators once at suite start and never delete during the run. The first half exists today (e2e/global-setup.ts clears once; all specs use the non-clearing preserveDataFirebasePage fixture). The intended second half — a complete shared data set loaded up front — was never implemented; instead each spec creates a timestamped user in beforeAll and builds groups/members through the UI.

Design

  1. Global setup runs against the isolated e2e emulators only (§3). It clears Auth + Firestore (+ Storage if receipt data is seeded) once — or starts them empty — then builds one deterministic data set — fixed names and amounts, no randomness — so tests can assert exact values.
  2. Users are created through the Auth emulator with emailVerified: true directly, so e2e no longer depends on the verifyUserEmail function. Tests sign in as a seeded user.
  3. Data ownership — the core rule for "a change in one test can't break a later test":
    • Read-only data: shared groups (with members, categories, expenses, payment history, rental data) that tests may read but never write.
    • Owned data: every test that mutates data gets its own seeded group (or user, if it mutates user-level state such as account preferences), named for the test (e.g. "History – delete payment"). Nothing else reads it.
    • Created-at-runtime data: tests that create new entities (new group, new member) use unique names, as today.
    • Assertions are scoped to the test's own group/user so stray data elsewhere can't affect them.
  4. Function triggers fire on seeded writes (createUserProfileOnSignUp, syncGroupMemberUids, linkInvitedMembers, sendPaymentNotificationEmail, email-lower syncs, …). The seeder must either wait for trigger side effects to settle before tests start, or write in a way that avoids/duplicates them deliberately. In particular, creating an Auth user triggers user-profile creation — the seeder must not race it.
  5. Reuse from scripts/db/: the emulator safety guard pattern and the ported allocation math in emulator-lib.ts, the ChunkedBatch writer and the "mark paid + write history the way the app does" logic in refresh-seed-expenses.ts. Not reused: its random expense generation. Shared helpers may be extracted so both the seed scripts and e2e use them.
  6. Remove the trap: delete the cleanFirebase and firebasePage fixtures (per-test wipes; unused, but the README tells new tests to use them) and fix the README.

5. Areas and the per-area command

The owner names an area; one command runs that area's unit tests and e2e tests. [my call] on the exact names and shape below.

Command: pnpm test:area <area> [<area> …], plus --unit / --e2e to run only one half. Full-suite commands (pnpm test, pnpm e2e:local) keep working.

Mechanism: a single area map (one file) lists, per area, the app source folders whose unit specs belong to it, the Cloud Functions specs (functions/src/*.spec.ts, run with the functions package's own Vitest) that belong to it, and the Playwright tag. E2E tests are tagged with Playwright's tag option (e.g. @expenses); app unit tests are selected by path (ng test --include); functions specs by file. A unit spec, functions spec or e2e test that matches no area should be detectable (so new code doesn't silently fall outside every area). Functions are in scope throughout (owner decision): their specs run with their area, count toward gap-filling (§6d), and fall under the CLAUDE.md rule.

Shared services, stores, directives and utilities are assigned to the area that primarily uses them; genuinely cross-cutting code (e.g. table filter directives, locale/allocation utilities) is listed under every area that depends on it, so touching it runs all of them. The builder decides the exact folder assignments.

6. Work breakdown

6a. Infrastructure first

  • Owner installs the Chromium build and coverage package (§3).
  • Neutralise real email sending for e2e (§3) — before any e2e run that touches invites, payments or the mail queue.
  • Isolated e2e emulator suite + e2e dev-server configuration (§3).
  • Shared data set + seeder in global setup (§4); fixture cleanup.
  • Area map, tags, test:area script (§5).

6b. Repair existing e2e specs

Run the suite (after the browser install) to get the real failure list — no meaningful run has happened yet. Triage each failure:

  • Stale test (selector, flow or text changed) → fix the test.
  • Feature removed → delete the test.
  • Looks like an app bug → report to the owner with evidence; don't change the assertion.

Bug handling [my call]: work on other areas continues; suspected bugs are batched and reported at the end of each area's repair rather than one interruption per bug. Until the owner decides, the test asserts the correct behaviour and is marked test.fail() with a comment describing the bug — it stays visible in every run and flips to an "unexpected pass" the moment the bug is fixed, which is the signal to remove the marker. "Full suite green" in §7 counts expected failures as green only when the owner has explicitly deferred that bug.

Move existing specs onto the shared data set as they're repaired (replacing build-it-through-the-UI setup where the UI flow isn't what the test is about). Re-evaluate the 3 currently skipped tests. Replace any waitForTimeout with condition waits.

6c. New e2e coverage

For each new area, cover the main happy paths and the integration points unit tests can't reach (Firestore round-trips, dialogs, navigation, function calls). Follow the existing pragmatic philosophy: critical paths, not every edge case. [my call]

6d. Unit-test gaps

61 of 173 app source files have no spec. Priority (substantive logic, roughly by size): features/admin/error-log, shared/directives/filters/* (base, select, toggle, text, date-range), services/calculator-overlay.service, features/expenses/rental/rental-grid and rental-edit-dialog, features/auth/account/{security,payments,preferences,legal}, services/admin-error-log / admin-mail / admin-reports, shared/components/loading/navigation-loading.service, stores with logic (group, user, member, category), date-plus-minus directive, guided-tour card/spotlight. Skip pure interfaces, type files and trivial one-liners. Cloud Functions are also in scope: functions/src has 11 specs covering parts of index.ts, admin-reports, receipt-ocr, receipt-parser, user-onboarding, common; the builder audits which exported functions in index.ts (invites, member linking, group/account deletion, mail queue, email syncs, scheduled cleanup) lack tests and fills the substantive gaps. Once the coverage package is installed, use the coverage report to find untested branches inside files that do have specs. [my call] on ordering and the skip list.

6e. Keep it current

  • CLAUDE.md rule (owner approved): whenever a feature is changed, update or add that area's unit and e2e tests in the same task, and run pnpm test:area <area> before calling the task done.
  • E2E section in ~/.claude/skills/pip-angular-testing/SKILL.md (owner decision: add to the existing skill, not a new one). Contents: the parallel-worker/data-wipe history and the shared-data ownership rules; the still-valid lessons from e2e/TESTING_PATTERNS.md (MDC selectors, test-id conventions, LoadingService waits, clipboard permissions, date inputs, avoiding fixed sleeps); emulator-ownership and env-var safety; how to run by area; new lessons learned during this work. Update the skill's description so it also triggers on Playwright/e2e work.
  • Docs: the skill becomes the source of truth for e2e patterns. e2e/TESTING_PATTERNS.md is retired (or reduced to a pointer) and e2e/README.md is trimmed to accurate how-to-run instructions (it currently references scripts that don't exist, e.g. pnpm e2e, pnpm test:full, and claims multi-browser runs). [my call]

7. Definition of done

  • Full unit suite passes.
  • Full e2e suite passes with 4 workers, three consecutive runs with no failures (flakiness check). [my call]
  • Every area passes when run alone via pnpm test:area <area>.
  • Every app bug found has been reported to the owner (and either fixed with their go-ahead or explicitly deferred).
  • CLAUDE.md rule and skill e2e section in place; README accurate.

8. Left to the builder

  • Isolated emulator mechanics: exact ports, demo-* project ID name, how Playwright starts/stops them (e.g. webServer entries or global setup/teardown), the Angular e2e configuration/environment, and how the functions build is ensured.
  • Seeder implementation: Admin SDK vs. emulator REST APIs, file location, how to wait for triggers. (If Admin SDK at the root needs firebase-admin as a root devDependency, hand the install to the owner.)
  • Exact contents of the shared data set, as long as it satisfies the ownership rules and gives each area what it needs.
  • Page-object structure (extend the existing POM; add page objects for new areas).
  • How to stub external calls (receipt OCR, email) in e2e.
  • Exact folder→area assignments and the test:area script's implementation language.
  • Ordering of work within each phase.
