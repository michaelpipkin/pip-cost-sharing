Users Read Lockdown — Design

pip-cost-sharing · 2026-10-23 · Status: approved by the owner on 2026-10-23 (answers in §11); ships in one release · Phase 3 (read half) of .claude/firestore-rules-hardening.md, merged with "link members by any verified address" (docs/superpowers/plans/2026-10-19-infra-followups.html, Owner section)

Tags: [my call] marks a choice made while drafting that the owner has not confirmed. The callable gatekeeper and the verifiedEmails/{address} index (server-only, one owner per address, most recent confirmation wins) are the owner's agreed designs and are not reopened here. Section 11 lists the questions.

1. Intent

firestore.rules still has allow read: if isSignedIn() on users/{userId}. Any signed-in account (sign-up is open) can read every profile's email, venmoId, paypalId, cashAppId, zelleId and emailOptOut, either one doc at a time or with a users list query. The write half of Phase 3 (B13, B14) is done. This design closes the read half.

Two client paths rely on querying users by email to auto-link invited members, so the lockdown and the owner's "link by any verified address" feature have to change the same code. Both move linking to the server and use the private index, so they ship as one plan.

2. Goals and non-goals

Goals

  1. A client can read only its own users/{uid} doc (plus the admin uid). Client queries on users are denied.
  2. Payment handles reach a payer only through a callable that checks the caller is an active member of the payee's group. It returns the four handles and nothing else.
  3. Auto-linking runs on the server through verifiedEmails/{address}. An invited member links to the account that has proven the address: its login email or a confirmed group email.
  4. No client writes another user's doc. The cross-user defaultGroupRef clears move to triggers, and the B13 exception rule is removed.
  5. Ships in one release (functions, rules and hosting together). Old open tabs are not a design concern at this app's size (owner, 2026-10-23); a reload fixes them.

Non-goals

  • A UI that lists or removes a user's verified addresses (follow-up).
  • Letting requestMemberEmailChange apply any indexed address without a confirmation mail. The index makes this easy, but it is a follow-up.
  • Per-caller limits on group mail, and removing the emulator admin uid from the production rules. Both are separate Owner items.
  • A consent step before an admin's auto-link (see Q2).

4. Proposed rules (release B)

// Server-only (Admin SDK). get() from other rules is not needed: no rule reads these.
match /verifiedEmails/{id}        { allow read, write: if false; }
match /paymentLookupLimits/{uid}  { allow read, write: if false; }

match /users/{userId} {
  function isOwnUserDoc() { return isSignedIn() && request.auth.uid == userId; }
  // No resource.data in the read rule: waitForServerCreatedUser listens to the
  // caller's own doc before it exists, and that get must pass.
  allow get:    if isOwnUserDoc() || isAdminUser();
  allow list:   if false;                 // no client queries users any more
  allow create: if isOwnUserDoc() && emailCreateValid() && userEmailCreateOwned();
  allow update: if isOwnUserDoc() && emailUpdateValid() && userEmailUpdateOwned();
  allow delete: if isOwnUserDoc();
}
  • isAdminClearingDefaultGroup() is deleted. No client writes another user's doc after release A.
  • Changes to the members rules. A client can no longer link anyone but itself, because it cannot read the index to learn a uid:
    • memberLinkCreateValid() becomes userRef == null || (own row && (email == '' || isOwnVerifiedEmail(email) || emailMatchesLinkedUser(after))). Keeping emailMatchesLinkedUser for the own row covers a creator whose stored profile email lags the token, so addGroup does not regress. [my call]
    • memberLinkUpdateValid(): userRef may change only from X to null, by an admin. The null-to-X path is removed. On an unlinked row an admin may still change email (with userRef staying null). The linked-row self-change is unchanged.
    • isUserDocRef() stays, because the own-row emailMatchesLinkedUser still uses it.
  • Release A adds only the two deny-all blocks, which document collections that are already denied by default. Every other rule stays as it is until release B.

5. Callables

5.1 getMemberPaymentMethods (new, functions/src/payment-methods.ts)

SignatureonCall<{ groupId?: unknown; memberId?: unknown }>(callableAppCheck, …) → { venmoId: string; paypalId: string; cashAppId: string; zelleId: string }
Auth checks, in order
  1. Signed in (unauthenticated).
  2. Both ids pass isDocId (invalid-argument).
  3. The caller's email is verified, by token claim or the Auth record as in verifiedCallerEmail (permission-denied).
  4. The group exists and request.auth.uid is in its activeMemberUids. Otherwise permission-denied with NOT_ACTIVE_MEMBER, the same message as group-emails.ts.
  5. groups/{groupId}/members/{memberId} exists (not-found). The member may be inactive, since an inactive member can still be owed.
  6. The rate limit is consumed after the checks, so refused calls don't count.
ReturnsThe four handles from users/{uid}, each '' when missing. All four are '' when the member is unlinked or the users doc is gone. Never email, emailOptOut or the uid.
Rate limit100 lookups per uid per 24 h window. It uses consumeRequestAllowance's transaction pattern on paymentLookupLimits/{uid} and refuses with resource-exhausted. Generalize that helper to take the collection and limit rather than copying it. The nightly deleteOldPaidExpenses deletes expired windows, as it does for memberEmailChangeLimits. [my call: 100/day]
ClientgetPaymentMethods(memberRef) calls it with memberRef.parent.parent!.id and memberRef.id. The summary's existing loading overlay and its "Could not load payment methods" snackbar cover a cold start and any failure.

5.2 linkInvitedMembers (changed)

The signature and the auth checks don't change. The caller is signed in and has a verified address (verifiedCallerEmail), otherwise failed-precondition. New behaviour:

  1. Upsert verifiedEmails/{caller's login address} for the caller. The client calls this after sign-up verification, after a verifyBeforeUpdateEmail change and on every Groups page load, so these calls are how the index learns login addresses.
  2. Link pending members for every address the uid owns in the index: collectionGroup('members') where emailLower in [...] and userRef == null, in chunks of 30 addresses. The email-equals-address re-check stays. Each group links at most one row (guard in §6.3).

It stays unthrottled, as today: it can only link the caller, to addresses the caller has proven.

5.3 Other callables touched

  • confirmMemberEmailChange: inside the existing transaction, also upserts verifiedEmails/{confirmed address} for the caller. After the commit it runs the linking routine for the caller, best-effort, so pending invites to that address link at once.
  • deleteUserAccount: deletes verifiedEmails where uid == uid before the users doc goes.
  • runAdminReport (orphaned-members) and repairOrphanedMembers: match through the index instead of users.emailLower. The "matched user count" becomes 0 or 1.

6. The verified-address index

6.1 Shape

verifiedEmails/{id} = { uid, email, verifiedAt: Timestamp, source: 'login' | 'group-confirm' | 'backfill' }. The id is the lowercased address with % encoded as %25 and / as %2F. SINGLE_EMAIL_PATTERN allows / in the local part, and a doc id cannot contain it. All index code goes in one module (functions/src/verified-emails.ts): verifiedEmailId, upsertVerifiedEmail, ownerOf, addressesOf, removeAllFor. [my call: escaped address, not a hash, so it stays readable in the console]

Upsert = takeover: set {uid, verifiedAt: now, …} unconditionally, so the most recent confirmation wins (owner rule). The backfill is the exception: it only creates and never takes over.

A login-email change does not remove the old address. The user did prove it, and a takeover handles a recycled address (Q5). The index takes addresses only from Auth-verified sources, never from users.email, so legacy unverified profile values cannot reach it.

6.3 Linking moves to the server

syncMemberEmailLower (the existing member-write trigger) also links. Keep the export name: a renamed function is a delete, and CI's firebase deploy --only functions --non-interactive stops at a deletion prompt.

  • When it links: the doc was created, or its email changed, and userRef is null and email is non-empty. An admin's unlink (X to null, same email) and account deletion's anonymize never re-link.
  • What it does: looks up ownerOf(emailLower). If the doc's email still equals the address, it writes userRef (and emailLower) in one update. The trigger runs again and finds nothing to do.
  • One row per account per group: skip, and log, when the uid is already in the group's memberUids. With several addresses an admin could add one person twice, and getMemberByUserRef assumes one row. linkInvitedMembers applies the same guard.
  • The client side (release A): addMemberToGroup keeps the in-group duplicate check and creates the member with userRef: null. The members listener shows the registered state when the link lands, about 1-2 s later. A Send Invite click in that window gets already-registered from sendGroupInvite.

The member email invariant (B19: a linked member's email is an address the linked user proved) holds by construction, because the index holds only proven addresses.

6.4 Default-group clears move to the server

  • syncGroupMemberUidsInternal already has the before and after memberUids. For each uid that left the list, it sets defaultGroupRef to null if it points at this group. This covers the removal path (#4).
  • A new clearDefaultsOnGroupDeactivate trigger (onDocumentUpdated('groups/{groupId}')) calls clearDefaultGroupRefs when active goes from true to false or archived from false to true. It ignores the membership-array updates. This covers #5.
  • Belt and braces: GroupService.resolveDefaultGroupRef also heals a default whose group is inactive. Today it heals only a missing group or an inactive membership. This covers the seconds before the trigger lands.

7. Migration and rollout

Prerequisite: the Plan 4 release (B13, B14, B19) is deployed, and its pre-release checklist (profile cleanup --apply, member-email audit) is done.

7.1 Deploy order: one release (owner decision, Q1)

Each CI run deploys functions, then rules and indexes, then hosting, so the rules flip a few minutes before the new client is served. The owner accepts that window. The original two-release order is kept below, struck through, for the record.

  1. Before merging: dry-run the backfill against production (read-only).
  2. The release (one merged PR): everything in §3-§6 plus the §4 rules.
  3. Right after CI finishes: run the backfill with --apply, then a dry run again (expect 0 to create). An invite added before the backfill still links on the invitee's next Groups load.
  4. Then: check firebase functions:list for the new functions, smoke-test the Pay dialog and adding a member by a registered address, and watch the function logs for getMemberPaymentMethods errors and linking skips.

Two releases:

  1. Before merging A: dry-run the backfill against production (read-only).
  2. Release A (functions + client + the two deny blocks): the index module and its writers, trigger linking, default-clear triggers, getMemberPaymentMethods, the client changes in §3. The A client works under the old rules and the new ones.
  3. Right after A's CI finishes: run the backfill with --apply, then a dry run again (expect 0 to create). Adds made between the deploy and the backfill still link: the invitee's next Groups load runs linkInvitedMembers.
  4. Wait 7 days. Watch function logs for getMemberPaymentMethods errors and for linking skips (one-row guard).
  5. Release B (rules only, plus rules specs and doc updates): §4. Afterwards, check app_errors for "Missing or insufficient permissions" from the paths in §7.2. Rollback = revert the PR. The A client runs fine on the old rules.

7.2 What an old open tab does (reference only; accepted by the owner)

After release A (rules unchanged), an old tab works fully, including its client-side linking. The stale-chunk prompt (navigation-loading.service.ts: "App Update Available", then a reload) appears only when the tab navigates to a lazy route whose chunk it hasn't loaded yet. A's hosting deploy removes the old hashed chunks. A tab that already loaded Summary and Members gets no prompt. The Android app (a WebView on the live site) behaves like a long-lived tab.

After release B, a tab still running the pre-A client fails these actions. B ships no hosting, so B itself never triggers the prompt.

7.3 Backfill script

scripts/db/queries/backfill-verified-emails.ts (pnpm query backfill-verified-emails [-- --apply]), with its logic in scripts/db/verified-email-backfill.ts and a verified-email-backfill.test.mjs, on the profile-email-audit pattern.

  • Targets production through lib.ts (ADC). The env-guard refuses to start while any *_EMULATOR_HOST is set. Dry run by default.
  • Source: Auth listUsers, accounts with emailVerified && email, skipping NON_USER_AUTH_EMAILS. Login emails are unique in Auth, so the source has no conflicts.
  • Plan per address: create when there is no entry, skip when the entry has the same uid, conflict when it has another uid. A conflict is reported and never overwritten, because a newer confirmation wins.
  • Reports, without writing: pending unlinked members whose address now has an owner (expected few, since linkInvitedMembers already covers login emails). They link on the owner's next Groups load or through the admin repair.
  • --apply uses chunked-batch.ts and refuses when Auth returned zero users. The second dry run must show 0 to create.

9. Risks

  • Old tabs and the Android WebView fail five actions after the flip (§7.2) until they reload. Accepted by the owner: the app has about 20 users a day and no active groups but the owner's.
  • The consent gap enables handle harvesting. An admin who knows someone's address can add them, which auto-links them, and then read their handles. The same is true today, and today anyone can read every user's handles. Mitigation: the per-uid limit bounds bulk harvesting. A consent step is Q2.
  • Trigger loops and races. A link write re-fires syncMemberEmailLower and syncGroupMemberUids. The re-runs are no-ops because email is unchanged and the arrays are recomputed. The link re-checks the doc's current email before writing.
  • A function rename looks like a deletion and blocks the non-interactive CI deploy. Keep the existing export names and only add new ones.
  • Cold start on the first Pay of a session: 1-3 s under the loading overlay. This is acceptable.
  • Address takeover moves a recycled address's future invites to its new owner (intended), and existing links stay as they are. An admin who types a secondary address learns whose it is (the owner's caveat; unchanged).
  • Rules get() semantics. The design removes every rules get() on other users' docs except the own-row emailMatchesLinkedUser. Per the Phase 2 lesson, the own-row creator test checks it on the emulator rather than relying on documentation.

11. Questions for the owner (answered 2026-10-23)

Owner answers: 1 one release, not two; 2 yes, show handles straight away (a handle only lets someone send money, never pull it); 3 the trigger; 4 triggers, and delete the B13 exception; 5 keep old login addresses; 6 keep the admin read.
  1. Two releases, with the rules flip 7 days after the code? Recommended: yes. A single release flips the rules before hosting serves the new client, and it breaks every pre-A tab and the Android WebView for five actions. Splitting also lets the rules be reverted on their own.
  2. Should payment handles of an auto-linked member be visible straight away? An admin can add anyone whose address they know and then read that person's handles. Recommended: yes for now, with the 100/day per-caller limit. That is far tighter than today, where every handle is readable. A consent step (handles shown only after the member has opened the group) would be a follow-up with its own flag.
  3. Link through the member trigger (async, about 1-2 s) or through a new add-member callable (synchronous)? Recommended: the trigger. It covers add, edit, admin batches and any future path with no new client API. The only cost is that the registered badge appears a moment after Save.
  4. Move the cross-user defaultGroupRef clears to triggers and delete the B13 exception rule? Recommended: yes, with the client self-heal kept as a fallback. Healing on the client alone would leave stale defaults in other users' data until they next sign in, and would keep the rule exception alive.
  5. Keep an old login address in the index after a login-email change? Recommended: keep it. The feature is "every address you proved", and a takeover handles recycling. The alternative is to remove it on change, which needs a "which address did this replace" hook in linkInvitedMembers.
  6. Keep the admin uid's read on users? Recommended: keep it, for parity with mail and app_errors. No current client path needs it, so dropping it is also safe.
