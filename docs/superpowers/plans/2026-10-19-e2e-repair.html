E2E Repair — Implementation Plan (Plan 2 of 4)

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps marked ☐ are checkboxes. Load the pip-angular-testing skill first — its "E2E (Playwright)" section is binding (rules, seed data, signInAs, running).

Goal: Every existing e2e spec passes against the current app, independently and in parallel, on the shared seeded data — so a red e2e run means a real regression.

Architecture: Each legacy spec is migrated off "create a user and build a group through the UI in beforeAll, then chain state through describe.serial" onto seeded datasets it owns plus read-only SHARED data, with signInAs. Stale selectors are replaced by data-testids (added to app templates where missing). Page objects lose their fixed sleeps.

Tech stack: Playwright 1.64, Angular 22 (signal forms), Firebase emulators via pnpm e2e, the Plan 1 seeder (e2e/seed/).

Spec: docs/superpowers/specs/2026-10-19-test-suite-design.html (§2 anti-goals, §4 data, §6b triage, §7 done).

Inputs: docs/superpowers/plans/2026-10-19-e2e-failures.html (baseline triage — read the section for your spec before starting), docs/superpowers/plans/2026-10-19-infra-followups.html (Plan 2 section).

Branch: e2e-repair, created from test-infrastructure (Plan 1 is not merged yet).

Global Constraints

  • All rules in the skill's E2E section apply: never clear data; shared is read-only; mutate only data your spec owns; unique runtime names; scope every assertion to your own data; tag every describe; isolated emulators only; no waitForTimeout; no mail to shared users.
  • No order dependence. No test.describe.serial and no state carried between tests (module-level variables set in one test and read in another). A multi-step user journey is one test. Every spec passes when run alone (pnpm e2e <file>), and every single test passes when run alone (--grep).
  • No conditional assertions. No if (await x.isVisible()) { expect… } — a test either asserts the element or doesn't involve it. (The baseline found a memorize test passing vacuously this way.)
  • Triage per spec §6b: stale test → fix the test; feature removed/moved → delete the test (record where coverage now belongs); looks like an app bug → keep the assertion of the correct behaviour, mark it test.fail() with a comment describing the bug, and list it in the task report with evidence. Never change an assertion to match broken behaviour.
  • Feature-tour must keep working. e2e/feature-tour/feature-tour.capture.ts uses AuthPage.gotoLogin, AuthPage.login, GroupsPage.goto, GroupsPage.createGroup, GroupsPage.selectGroup, MembersPage.goto, MembersPage.addMember and ../fixtures. Keep those methods' signatures and behaviour (removing sleeps is fine). pnpm exec playwright test -c e2e/feature-tour/playwright.feature-tour.config.ts --list must still list 14 tests. Never run it (it targets the dev emulators).
  • App template changes are limited to adding data-testid attributes (and, for a confirmed app bug, only with the owner's go-ahead). Test IDs follow the existing kebab-case style.
  • New seeded emails end in @pipsplit.test; new group names are unique across all datasets and start with the spec's area (e.g. "Groups – Manage A").
  • Never touch the default emulator ports. No pnpm install/add/downloads. Commit messages end with [no-deploy] (testid-only template changes included) and the Co-Authored-By trailer.
  • After each task: pnpm test:area <areas touched> passes (unit + functions + e2e for those areas), cd e2e && pnpm exec tsc --noEmit -p . is clean, pnpm test:area --check exits 0.

Review Focus

  1. Running one test alone. A test that only passed because an earlier test created its data. Pinned in every spec task by: run each repaired file alone, then pnpm e2e <file> --grep "<one test title>" for the last test in the file.
  2. Parallel neighbours. Two workers running specs that touch the same group or recipient. Pinned by the ownership table below (no group owned by two specs) and Task 8's full runs at 2 and once at 4 workers.
  3. Vacuous passes. Assertions guarded by visibility checks, or tests whose setup silently skips. Pinned by Task 7's grep gate: zero matches of if \(await .*\.isVisible\( in e2e/ outside feature-tour/.
  4. Cold start. The first test in a worker hits a still-compiling dev server or cold functions. Pinned by running each repaired file alone twice (each run starts cold).
  5. Feature-tour breakage. Page-object edits change a method feature-tour relies on. Pinned by the --list + tsc check in Tasks 3, 4 and 7.
