Goal: The substantive app code and Cloud Functions that have no tests today get unit and functions tests that would fail if their behaviour broke. Files that have specs but leave large branches untested get those branches covered. Every bug the tests expose is pinned and reported, and fixed only with the owner's go-ahead.

Architecture: Phase A (Tasks 1–15) writes tests only. Shared test plumbing goes in src/testing/test-helpers.ts and functions/test/. Cloud Function handlers are driven through their own .run(request|event) against the isolated emulators, so no handler is restructured just to make it testable. Phase B (owner-approved fixes) changes app or functions code one fix at a time, and each fix flips its pinned test from it.fails to it.

Global Constraints

  • Phase A changes no app or functions logic.
    • Allowed in src/ and functions/src/: new *.spec.ts files and changes to existing specs, test helpers, and exporting an existing private helper only where a task says so.
    • Tooling under scripts/, e2e/ infra and config files may be fixed. That is our own test infrastructure.
  • Bug triage (spec §2 anti-goal "tests bent to match bugs"): when code looks wrong:
    • write the test that asserts the correct behaviour;
    • mark it it.fails(...) (Vitest) with a // BUG: comment naming the file:line and the Phase B item;
    • list it in the task report.
    Never assert the broken behaviour as if it were intended. The suspected bugs in the appendix are leads, not verdicts: confirm each against the code before pinning, and report any that turn out to be wrong.
  • Unit specs run in one shared jsdom context (isolate: false).
    • Never vi.resetAllMocks(). Use vi.spyOn plus vi.restoreAllMocks() in afterEach.
    • vi.mock is not available in app specs.
    • Restore real timers after vi.useFakeTimers().
    • Remove any CDK overlay pane a test created. Destroy the fixture, and if needed call TestBed.inject(OverlayContainer).ngOnDestroy().
  • Functions specs run against the shared isolated emulators. Global setup clears them once per run, never per test.
    • Every test uses its own random ids, emails and group ids, and asserts only on its own documents. Never count a whole collection; take deltas where a builder counts globally.
    • vi.mock is allowed in functions specs (plain Node Vitest), e.g. for nodemailer.
    • Handlers are invoked with handler.run({ auth, data } as any) or trigger.run({ data, params } as any). Errors are HttpsError; assert .code.
  • Every new spec is registered in scripts/test-area/areas.mjs under the area(s) whose code it covers. Shared code goes in every area that imports it (follow the existing ...MEDIA_QUERY / ...ALLOCATION_UTILS pattern). pnpm test:area --check must pass.
  • Isolated emulators only (project demo-pipsplit-test, ports 19099/18080/19199/15001). Never the default ports. Set *_EMULATOR_HOST before any firebase-admin initialisation. No pnpm install/add or downloads; hand those to the owner.
  • Conventions (CLAUDE.md) apply to every spec and any touched file:
    • signals, protected readonly injects, @if/@for, no rxjs in new code;
    • pnpm only;
    • docs in HTML.
  • Tests must bite: every test fails if the behaviour it names broke. No assertion that passes on any value, no test that only checks toBeTruthy() on a created component, and no assertion on mock call counts that the test itself arranged.
  • Commits: Phase A messages end with [no-deploy] (tests and tooling only). Phase B fix commits do not, because they change app behaviour. Every message ends with the Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com> trailer.
  • After each task:
    • pnpm test:area <areas touched> --unit passes, for app specs.
    • pnpm --dir functions test passes, for functions specs.
    • pnpm test:scripts passes, for scripts.
    • pnpm test:area --check passes.
    • Each new spec file passes alone and as part of the full pnpm test run. That catches leaks in the shared jsdom context.

Review Focus

  1. Leaks in the shared jsdom context: a spec that leaves a CDK overlay pane, a fake timer, a globalThis.matchMedia override or an unrestored spy makes unrelated specs fail depending on file order. Pinned by Task 7, where each overlay spec asserts .cdk-overlay-container has no panes after the test, and by every task's "passes alone and in the full run" check.
  2. Shared emulator data in functions specs: handlers such as deleteUserAccount, syncAuthEmailsToUsers, deleteOldPaidExpenses, logAppError and the reports scan whole collections. A test that counts globally flakes as other specs add data. Pinned by Tasks 9–12, which assert on own ids and use before/after deltas.
  3. Clock- and locale-dependent logic:
    • date shortcuts (t);
    • the custom date adapter's "current year";
    • the 90-day receipt cutoff;
    • the 30-day and monthly report windows;
    • the invite 24 h cooldown.
    Any of these tests passes or fails depending on the day it runs. Pinned by fixed system time (vi.setSystemTime), dates relative to "now" in emulator data, and named boundary tests in Tasks 3, 11 and 12.
  4. Mocks that diverge from the real API: a unit test green against a mock that behaves unlike Firebase (mock Timestamp, mock DocumentReference paths) proves nothing. Pinned by the coverage-pass tasks (13, 14), which assert service calls with real argument shapes (collection paths, where fields), and by functions tests, which run against the real emulator.
  5. Pinned bugs left behind after a fix: an it.fails whose bug is fixed makes the run fail, which is the point. A Phase B fix that forgets to flip its pin, or deletes the test, loses the coverage. Pinned by each Phase B task removing exactly its markers and keeping the assertion.
