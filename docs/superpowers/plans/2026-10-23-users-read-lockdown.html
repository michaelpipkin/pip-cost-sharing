Users Read Lockdown Implementation Plan

pip-cost-sharing · 2026-10-23 · Phase 3 (read half) + the verified-address index · branch users-read-lockdown off dev

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (- [ ]) syntax for tracking.

Goal: A client can read only its own users doc; payment handles come from a membership-checked callable; invited members link on the server through a private index of every address a user has proven; no client writes another user's doc.

Architecture: A server-only verifiedEmails/{id} index (one owner per address, most recent proof wins) is written by the sign-up trigger, linkInvitedMembers, confirmMemberEmailChange and a one-off backfill. The existing member-write trigger links new or re-addressed unlinked rows through it. Payment handles move behind getMemberPaymentMethods; default-group clears move into triggers; the rules then deny every cross-user read and write.

Tech stack: Angular 22 (zoneless, signals, no RxJS), Firebase Functions v2 (Admin SDK), Firestore rules, Vitest (app and functions), Playwright e2e and node:test (scripts) on the isolated test emulators.

Spec: docs/superpowers/specs/2026-10-23-users-read-lockdown-design.html (approved 2026-10-23; owner answers in §11). Read it with this plan: section references below (§n) point into it.

Global Constraints

  • One release (owner): functions, rules and hosting in one PR. No old-client or stale-tab analysis anywhere in code comments, docs or tests.
  • Never rename or remove an exported function. CI's non-interactive functions deploy stops at a deletion prompt. Add new exports only; syncMemberEmailLower keeps its name while gaining linking.
  • The index takes addresses only from Auth-verified sources (a verified token or Auth record, or a confirmed group-email token), never from users.email.
  • Index doc id: the lowercased address (normalizeEmail), then % → %25, then / → %2F (that order).
  • Index doc shape: { uid: string, email: string (lowercased), verifiedAt: Timestamp, source: 'login' | 'group-confirm' | 'backfill' }. An upsert overwrites (takeover); only the backfill is create-only.
  • Payment lookup limit: 100 per uid per 24 h window from the first lookup, collection paymentLookupLimits/{uid}, refusal resource-exhausted with "You've looked up too many payment details today. Try again tomorrow."
  • One row per account per group: no linking path may give one uid two member rows in one group.
  • CLAUDE.md conventions: signals, @if/@for, no RxJS, protected readonly injects, Document References over ids, pnpm.
  • Tests: write each test first and see it fail. Functions and e2e only on the isolated test emulators (demo-pipsplit-test); check the test ports are free first. Rebuild functions (pnpm --dir functions run build) before e2e. Specs never delete emulator data, never mail the shared users.
  • Commits: stage by explicit path. Code commits without [no-deploy]; test- or doc-only commits with it. Every commit ends with Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>. No push, merge or deploy; no production access.

Review Focus

Inputs the design implies but doesn't spell out, most likely first. Each has a test in the owning task, marked (RF n).

  1. Addresses with /, %, + or capitals must round-trip through the id and still link: Ann/B+c%d@Example.com links a row stored as ann/b+c%d@example.com. (T1, T3)
  2. Two rows for the same person added at the same moment under two of their addresses: both triggers run concurrently and exactly one row links. (T3)
  3. An email changed twice before the trigger runs: the trigger for the first change must not link the row to the first address's owner. (T3)
  4. A payee whose account was deleted (row anonymized to userRef: null, or userRef pointing at a missing doc): the Pay dialog opens with no handles and no error. (T5)
  5. Unarchiving or renaming an inactive group must not clear anyone's default again, and the membership-array update that syncGroupMemberUids writes must not trigger a clear. (T4)

Rules for linkMemberByVerifiedEmail (§6.3):

  • not-applicable unless: after.userRef is null, after.email is non-empty, and either before is undefined (create) or normalizeEmail(before.email) !== normalizeEmail(after.email). So an unlink (X → null, same email) and account-deletion anonymizing never link.
